### Worktree and cache cleanup

Deletion is part of a requested cleanup. Inspect the candidates before approving the exact targets. A disk-usage question starts with an audit and does not authorize deletion.

1. Read the repository instructions and relevant Just recipes. Record disk usage, then run the installed `scripts/worktree-audit.sh <repo> --base <local-base> --json`. It reads local Git state without fetching, calling a forge, or reading chat stores. It lists the main worktree, locks, commit reachability, and tracked, untracked, and ignored files. The base ref and remote-tracking refs may be stale.
2. Establish current base and PR state through the repository's actual forge when needed. A closed PR does not prove its commits merged. A squash-merged PR needs separate verification because ancestry alone cannot establish equivalence. Unknown or unavailable evidence remains unknown. The helper accepts normalized PR data through `--pr-data` and known active paths through repeated `--active` arguments.
3. Check activity through the current runtime's project threads, named worker worktrees, and processes. Do not infer inactivity from a clean Git status or missing transcripts. Never delete a locked or active worktree, the main checkout, or a parent directory containing other projects. If activity cannot be established, hold that candidate and explain what is missing.
4. Inspect all local files before deleting. Tracked changes, untracked source, and ignored credentials or artifacts can hold unique work. Show relevant diffs and names without printing secrets. Classify ignored entries by inspecting their purpose. Do not declare an untracked file disposable merely because Git does not track it. Back up retained material outside the target and verify the backup before removal.
5. Present the concrete list with each exact path, recoverable commit refs, local files to retain or discard, activity evidence, and reason for removal. A broad cleanup request requires confirmation of this list. Existing approval for the same exact targets and known file disposition remains valid. Changes discovered after approval require a new decision for those changes.
6. Recheck Git status, ignored files, locks, and activity immediately before each removal. Use `git worktree remove -- <exact-path>` first. Use `--force` only when the approved file disposition requires it. Do not use recursive removal as a fallback after an unexplained Git error. Do not delete branch refs as a cleanup side effect. Prune stale Git metadata only for the approved worktrees.
7. For caches or simulators, inspect the actual directories or IDs, contents, and active processes first. Apply the same target approval and file-disposition rules. Use platform-specific commands only on the platform where they apply. Do not expand worktree cleanup into deleting all simulators, package caches, or editor state.
8. Report disk usage before and after, the targets removed, and why each remaining candidate was held. Keep the audit and approval record with the task's handoff when the work needs to resume.

The helper's `candidate-clean-merged` bucket is a candidate for review. It cannot establish chat activity, fresh remote state, or deletion authorization. `hold-files` includes ignored entries such as build output, which can be approved for disposal after inspection.
